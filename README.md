# LootOverflow

Мод для Minecraft 1.20.1 (Forge) для проблемы переполнения сундуков лутом,
когда несколько модов вместе добавляют в лут-таблицу данжа/структуры больше
предметов, чем есть слотов в сундуке (27/54) — и лишнее просто пропадает.

## Как это работает

1. **Перехват генерации лута.** Ванильный `RandomizableContainerBlockEntity`
   (сундук, бочка) хранит несгенерированные `lootTable`/`lootTableSeed` и
   разворачивает их в момент первого обращения к содержимому, помещая предметы
   ровно в 27/54 слота — всё, что не влезло, теряется. `LootFillHandler`
   перехватывает клик по сундуку/бочке ДО того, как ванильный код это сделает,
   сам генерирует список предметов лут-таблицы (`LootTable#getRandomItems`),
   объединяет одинаковые стаки (как это делает ванильный алгоритм) и
   распределяет: первые N предметов — в реальные слоты, остальное — в
   `OverflowInventory`.
2. **Хранение скрытого лута.** `OverflowInventory` — это Forge-capability,
   прикреплённая к блок-энтити сундука/бочки (`OverflowAttachHandler`).
   Она реализует `INBTSerializable`, поэтому Forge автоматически сохраняет её
   в NBT сундука (`ForgeCaps`) при каждом сохранении мира — отдельная
   сетевая синхронизация или сохранение не нужны.
3. **GUI с индикатором.** Ванильный `ChestMenu` нельзя ни унаследовать (его
   конструктор недоступен для этого), ни добавить в него слот, поэтому
   `ContainerOpenHandler` даёт ванильному коду открыть обычное меню (это
   гарантирует, что все проверки других модов — защита территории, права
   доступа и т.д. — отработают как обычно), и сразу же, как только это меню
   открылось, подменяет его на `OverflowChestMenu` — тот же контейнер (для
   двойного сундука — оба блок-энтити), плюс один дополнительный слот-индикатор
   в самом низу окна, который существует только если есть скрытый лут.
4. **Извлечение.** Клик по индикатору достаёт последний предмет из
   `OverflowInventory` и кладёт его в свободный слот сундука или, если сундук
   полон, в инвентарь игрока. Если игрок вручную освобождает слот сундука
   (обычным кликом, шифт-кликом), в него автоматически подтягивается
   следующий скрытый предмет — реализовано в `OverflowChestMenu.clicked` /
   `quickMoveStack`.

## Совместимость

- **Lootr.** Мод намеренно НЕ трогает блоки из пространства имён `lootr:` —
  ни на этапе генерации лута, ни на этапе подмены GUI. Lootr генерирует
  независимый лут для каждого игрока из одного и того же сундука; если бы
  этот мод один раз "съедал" `lootTable`/`lootTableSeed`, второй и следующие
  игроки перестали бы получать свою версию лута. Поэтому для сундуков Lootr
  этот мод просто не активируется — Lootr продолжает работать как обычно,
  без переполнения (у него своя логика на этот счёт). Это осознанное решение,
  а не недоработка: индивидуальный лут на игрока — это механика честности для
  мультиплеера, и "доливать" туда весь лишний лут через переполнение
  противоречило бы её смыслу. Если оба мода всё же установлены вместе,
  `LootrConflictWarning` пишет предупреждение в лог сервера при старте и
  присылает сообщение в чат операторам при входе — чтобы это не выглядело
  как незаметный баг.
- **Другие моды.** Обработчик `LootFillHandler` подписан с приоритетом `LOW`
  и сразу выходит, если событие уже отменено — то есть любой мод защиты
  территории/прав, отменяющий клик по сундуку, отработает раньше и полностью
  заблокирует и генерацию лута, и открытие GUI. `ContainerOpenHandler` тоже
  реагирует только на уже успешно открытое ванильное меню — если какой-то мод
  не дал открыть сундук, до нашего кода дело не дойдёт.

## Публичный API для аддонов

Основная логика намеренно разбита так, чтобы сторонний мод-мост мог дать
такую же защиту от переполнения контейнеру ИЗ ДРУГОГО мода (например, если
у кого-то появится API Lootr под конкретную версию и он захочет написать
для него отдельную интеграцию), не переписывая её с нуля:

- `com.lootoverflow.api.LootOverflowApi` — чистые статические функции без
  привязки к конкретному блоку: `buildChestLootParams`, `generateMergedLoot`,
  `splitForCapacity`. Берут лут-таблицу и сид, отдают список "что видно" и
  "что переполнилось".
- `LootOverflowCapabilities.attach(event, blockEntity)` — навешивает такое же
  NBT-сохраняемое хранилище `OverflowInventory`, как у ванильных сундуков,
  на любой блок-энтити из `AttachCapabilitiesEvent<BlockEntity>` стороннего
  мода.
- `com.lootoverflow.menu.OverflowChestMenu.createServer(...)` — тот же GUI со
  слотом-индикатором, принимает произвольный `Container` и список источников
  `OverflowInventory`.

Важный нюанс для интеграции с системами по-игрочного лута (как у Lootr):
`OverflowInventory` в этом моде — один список на блок-энтити, потому что у
ванильного сундука лут общий на всех. Для по-игрочного лута мосту нужно
хранить отдельный `OverflowInventory` на каждого игрока (например,
`Map<UUID, OverflowInventory>` в своей capability), а не переиспользовать
один и тот же объект — сами функции для генерации/разбиения лута это никак
не ограничивает, они ничего не знают про "сундук" или "игрока".

Реального моста к Lootr в этом репозитории нет — только эта подготовленная
точка расширения. Написать сам мост без верифицированного доступа к API
Lootr нужной версии было бы гаданием вслепую, которое рискует незаметно
сломать его собственную логику лута, а не просто не собраться.

## Известные ограничения первой версии

- Автодозаполнение освободившегося слота работает через клики в GUI сундука.
  Если предмет из сундука забирает не игрок в открытом окне, а, например,
  воронка (hopper), скрытый лут в освободившийся слот сама не переместится —
  переместится только при следующем открытии сундука игроком.
- Часть API вызывается через reflection с проверкой наличия метода в рантайме
  (`LootTable#getRandomItems`, `ChestBlock#getContainer`) — это защита от
  падения сборки/игры, если конкретная сборка Forge 1.20.1 будет отличаться
  сигнатурой метода; если метод не найден, в лог пишется предупреждение и
  мод для этого случая аккуратно деградирует (защита от переполнения
  отключается только там, где не сработал конкретный метод), а не падает.
- В этой песочнице нет доступа к Maven Forge/Minecraft (сеть заблокирована
  политикой окружения), поэтому реальная сборка `gradlew build` здесь не
  запускалась — код подготовлен по стандартной структуре Forge MDK. GitHub
  Actions (см. выше) собирает его на обычном окружении с полным доступом в
  интернет — там сборка либо пройдёт, либо покажет реальную ошибку компиляции,
  которую можно будет поправить.

## Сборка

### Через GitHub Actions (не нужен мощный компьютер)

При каждом push в репозиторий `.github/workflows/build.yml` автоматически
собирает мод на серверах GitHub. Готовый `.jar` появляется во вкладке
**Actions → (последний прогон) → Artifacts → lootoverflow** — просто
скачиваете и кладёте в папку `mods/`. Компилировать локально не нужно.

### Локально

```
./gradlew build
```

Первая локальная сборка ForgeGradle — тяжёлая (скачивает и декомпилирует
Minecraft, патчит под Forge): нужно несколько ГБ свободного места на диске,
желательно 4+ ГБ свободной оперативки под Gradle, и от 15 минут до часа
времени на слабом железе. Повторные сборки — быстрые за счёт кэша.

Соберётся `build/libs/lootoverflow-1.0.0.jar` — устанавливается как обычный
Forge-мод (`mods/`) на клиент и сервер (обязателен на сервере, желателен на
клиенте — свой собственный экран сундука).

Для локальной разработки: `./gradlew runClient` / `./gradlew runServer`.
